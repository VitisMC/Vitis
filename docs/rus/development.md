# Окружение разработчика

[English](../eng/development.md) · [Документация](README.md)

## Сборка и тесты

Нужны Go 1.23+ и Git. Выполняйте команды из корня репозитория.

Linux (Bash):

```bash
go mod download
go build ./...
go test ./... -count=1
go vet ./...
make docs-check
```

Windows (PowerShell 7.2+):

```powershell
go mod download
go build ./...
go test ./... -count=1
go vet ./...
go run ./cmd/vitis-doccheck
```

Сборка и тесты используют сгенерированный Go-код из Git. При запуске сервер сам подготавливает отсутствующие ресурсы Minecraft без Java; см. [установку](getting-started.md). Для полной перегенерации нужны Java и дополнительные инструменты.

Для запуска из исходников используйте `go run ./cmd/vitis -config vitis.yaml`. Скрипт `scripts/linux/run.sh` собирает весь пакет сервера и запускает бинарник, передавая аргументы и сигналы. `make run` использует пример конфигурации из репозитория; проверьте его настройки перед запуском.

## Скрипты сборки и запуска

Linux (Bash):

```bash
./scripts/linux/build.sh
./scripts/linux/run.sh -config configs/vitis.yaml
make verify
```

Windows (PowerShell 7.2+):

```powershell
pwsh -NoProfile -File .\scripts\windows\build.ps1
pwsh -NoProfile -File .\scripts\windows\run.ps1 -config configs\vitis.yaml
pwsh -NoProfile -File .\scripts\windows\verify.ps1
```

`build.ps1` принимает необязательный путь выходного файла, например `build.ps1 "build\vitis.exe"`. `run.ps1` передаёт аргументы сервера и ввод из консоли. `stop` сохраняет мир и завершает процесс. Скрипты сборки и запуска используют корень репозитория как рабочий каталог.

`verify.ps1` выполняет те же проверки, что `make verify`, без Make. Для обнаружения гонок нужны cgo и совместимый C-компилятор; см. [требования для Windows](generators/README.md). Скрипты не меняют политику выполнения PowerShell.

Скрипты платформ находятся в `scripts/linux/` и `scripts/windows/`. Описание генерации и Go-тесты в `scripts/` общие.

## Карта репозитория

| Область | Назначение |
| --- | --- |
| `cmd/vitis` | Создание подсистем сервера, запуск и остановка |
| `cmd/vitis-data` | Java-генерация ресурсов Minecraft и отчётов для разработчика |
| `cmd/vitis-worldgen-compare` | Сравнение с чанком из оригинального Minecraft |
| `cmd/vitis-doccheck` | Проверка документации без доступа к сети |
| `internal/network`, `internal/protocol` | Сеть и кодирование пакетов |
| `internal/session` | Состояния протокола, жизненный цикл игрока и игровые обработчики |
| `internal/world` | Измерения, симуляция, чанки и сохранение |
| `internal/entity` и пакеты игровых механик | Сущности и игровые правила |
| `internal/data/generated` | Сгенерированные данные в Git |
| `internal/data/generator` | Генераторы; многие имеют тег сборки `ignore` |
| `internal/datapack` | Поиск, проверка и публикация ресурсов |

Перед изменением доступа к состоянию или остановки сервера прочитайте [архитектуру](architecture.md). Добавление команд, пакетов и механик описано в [практических руководствах](extending.md).

## Процесс изменений

Следуйте [CONTRIBUTING](../../CONTRIBUTING.md): создавайте ветки от `dev`, направляйте PR в `dev`, используйте принятые префиксы веток и Conventional Commits. До правок проверьте результаты тестов; сохраняйте чужие незакоммиченные изменения.

Используйте принятые в Go подходы и существующую модульную структуру. Разделяйте обработку протокола, игровую логику и хранение данных. Добавляйте абстракции только для конкретной задачи.

Для новой логики пишите тесты, включая граничные случаи. Для конкурентного кода проверяйте гонки, для сетевых кодеков — некорректные входные данные. Документационные комментарии Go пишутся на английском; форматирование — gofmt. Для логирования используйте `internal/logger` со структурированными полями.

## Изменение документации

Обновляйте оба языка при изменении поведения. В каждом справочнике конфигурации должна быть одна строка на каждый конечный YAML-ключ, записанный в обратных кавычках в первой ячейке. Вместо копирования больших реализаций давайте ссылки на исходники.

`make docs-check` проверяет цели ссылок, парность страниц и покрытие ключей конфигурации. Перевод, ссылки на разделы и внешние сайты проверяются вручную. Полная проверка проекта описана в [тестировании](testing.md).
